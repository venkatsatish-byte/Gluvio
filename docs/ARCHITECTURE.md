# Architecture

This document covers the app's structure, data model, and the HealthKit, sync
and safety decisions behind it. Code comes after the open questions in
[MVP_SCOPE.md](MVP_SCOPE.md) are answered.

## 1. Guiding decisions

These are the choices that shape the rest of the design. Most are driven by
platform limits that are easy to miss until late in a health app.

1. **Apple Health is the source of truth for glucose; the app keeps a local mirror.**
   Readings from CGMs, Bluetooth meters and manual entries all land in Apple Health.
   The app writes its manual entries there too, then mirrors every glucose sample
   into SwiftData using an anchored query (`HKAnchoredObjectQuery`). The mirror
   makes charts and statistics fast, lets widgets read a snapshot, and lets
   deletions made in the Health app flow through.

2. **Don't sync health data through the app's own iCloud container.** App Store
   Review Guideline 5.1.3(ii) says apps "may not store personal health information
   in iCloud". So the "optional iCloud sync" from the brief should be done this way:
   - Glucose, carbs, water and meals are written to Apple Health, which already
     syncs end-to-end encrypted across the user's devices.
   - App-only data (meal photos, notes, reminders, how each meal affected glucose)
     stays on the device, and the mirror can be rebuilt from Health on a new phone.
   - Preferences that aren't health data (units, chart range) can sync through
     `NSUbiquitousKeyValueStore`.

   Check the current wording of the guideline before submitting; this is the
   single most likely reason for a rejection if it's gotten wrong.

3. **Time in range is only computed from CGM data.** Time in range assumes
   continuous readings. With fingersticks alone, the app shows
   "% of readings in range" instead, labeled differently, because fingerstick
   readings cluster at fasting and before meals and skew the result.

4. **A1C is shown as an estimate, with the formula that fits the data.**
   - With at least 14 days of CGM data covering at least 70% of the time, show
     the **Glucose Management Indicator** (GMI = 3.31 + 0.02392 × mean mg/dL), the
     international consensus measure.
   - With fingersticks only, show an "estimated A1C" from the ADAG formula
     (A1C = (mean mg/dL + 46.7) / 28.7), only after a minimum number of readings
     spread across the day, with a note on its limits.
   - Every A1C figure says it is an estimate, never a lab result.

5. **Out-of-range alerts are informational, not safety alarms.** Two platform facts
   drive this:
   - **CGM data reaches Apple Health late.** Some CGM apps write to Health with a
     delay (Dexcom's US apps have historically delayed HealthKit data by about
     3 hours). Other apps, such as FreeStyle Libre, vary by region and app version.
   - **Background updates are rationed.** iOS and watchOS limit how often a
     background HealthKit observer and a complication can refresh.

   So a Watch "out of range" haptic can't be timely or reliable enough to protect
   someone from a dangerous low. The CGM maker's own app remains the alarm. Every
   reading the app shows carries its age ("12 min ago"), and anything older than
   a threshold is visibly marked as stale. Showing and alerting on real-time CGM
   data can also fall under FDA rules for CGM "secondary displays", so it needs
   regulatory advice before shipping (see MVP_SCOPE.md).

6. **HealthKit has no trend arrows.** Apple Health stores CGM values but not the
   CGM's trend arrow. The app derives the arrow from the slope of the last 15–20
   minutes of CGM readings, using the standard rates (about ±1, ±2 and
   ±3 mg/dL per minute), and shows no arrow for fingersticks or sparse data.

7. **No network code at all in the MVP.** The app has no account, no backend and
   no analytics SDK. That keeps the privacy story simple to state ("your data never
   leaves your device or your Apple Health") and makes the App Store privacy label
   "Data Not Collected".

## 2. Targets and modules

```
┌──────────────────────── Xcode project (generated by XcodeGen) ────────────────────────┐
│                                                                                         │
│  iOS app            iOS widgets         watchOS app          watchOS widgets           │
│  (SwiftUI)          (WidgetKit)         (SwiftUI)            (complications)           │
│     │                   │                   │                      │                    │
│     └─────────┬─────────┴───────────┬───────┴──────────────────────┘                    │
│               ▼                     ▼                                                    │
│      GlucoseKit (local Swift package, shared by every target)                            │
│      ├── Core        models, units, glucose ranges, safety thresholds (no Apple frameworks) │
│      ├── Analytics   time in range, GMI and estimated A1C, meal response, trend arrow    │
│      ├── Health      HealthKit service: protocol, live and mock implementations          │
│      └── Storage     SwiftData schema, repositories, App Group snapshot for widgets      │
└─────────────────────────────────────────────────────────────────────────────────────────┘
```

- **The shared package keeps logic in one place.** The iPhone, Watch and widgets
  all classify a reading the same way, because they all use the same `GlucoseRange`
  and `Analytics` code.
- **`Core` and `Analytics` are plain Swift** with no UIKit, HealthKit or SwiftData.
  They're where the medically sensitive math lives, so they get the heaviest unit
  tests, and those tests can run without a simulator.
- **XcodeGen** (`project.yml`) generates the `.xcodeproj`, so the project is a
  readable text file in Git instead of an opaque project file that conflicts on
  every change.
- **An App Group** (`group.<bundle-id>.shared`) holds a small JSON snapshot
  (latest reading, today's stats) that widgets and complications read. Widgets
  never query HealthKit or SwiftData directly; that keeps their timelines fast
  and within their memory limits.

## 3. MVVM in practice

- **Views** are SwiftUI and hold no logic beyond layout and formatting.
- **View models** are `@Observable` classes (iOS 17 Observation), one per screen,
  marked `@MainActor`. They call services and expose ready-to-display state such
  as `DashboardState`.
- **Services** are `actor`s or `Sendable` types behind protocols: `HealthService`,
  `GlucoseRepository`, `MealRepository`, `ReminderScheduler`, `ReportRenderer`.
  Using protocols means previews and tests run against mock data with no
  HealthKit involved.
- **Dependency injection** goes through a single `AppEnvironment` container
  passed into the SwiftUI environment. No singletons except Apple's own.

```
View ──binds──▶ ViewModel (@Observable, @MainActor)
                    │ async calls
                    ▼
        ┌──────── Services (protocols) ────────┐
        │ HealthService      GlucoseRepository │
        │ ReminderScheduler  ReportRenderer    │
        └──────┬──────────────────┬────────────┘
               ▼                  ▼
          HealthKit          SwiftData store ──▶ App Group snapshot ──▶ Widgets
```

## 5. Data model

All glucose values are **stored in mg/dL** as `Double` and converted only for
display. mmol/L = mg/dL ÷ 18.0156, from glucose's molar mass of
180.156 g/mol. HealthKit uses the same molar mass, so values never drift when
the user switches units.

### Value types (GlucoseKit/Core)

```swift
enum GlucoseUnit: String, Codable { case mgdL, mmolL }

enum ReadingContext: String, Codable, CaseIterable {
    case fasting, beforeMeal, afterMeal, bedtime, other
}

enum ReadingSource: String, Codable {
    case manual        // typed into this app
    case cgm           // continuous monitor, via Apple Health
    case meter         // Bluetooth meter or another app, via Apple Health
}

enum GlucoseBand: Comparable {   // where a reading falls against the user's targets
    case urgentLow, low, inRange, high, urgentHigh
}

struct TargetRange: Codable {
    var low: Double = 70          // mg/dL, editable
    var high: Double = 180        // mg/dL, editable
    var urgentLow: Double = 54    // consensus "level 2" low
    var urgentHigh: Double = 250  // default; confirm with clinical reviewer
}
```

### Stored models (SwiftData, GlucoseKit/Storage)

| Model | Key fields | Notes |
|---|---|---|
| `GlucoseReading` | `id`, `date`, `mgdL`, `context`, `source`, `sourceName`, `healthKitUUID?`, `note` | Mirror of Apple Health. `context` for readings from other apps defaults to `.other` and can be set by the user. |
| `Meal` | `id`, `date`, `kind` (breakfast/lunch/dinner/snack), `carbsGrams`, `items: [MealItem]`, `photo?` (external storage), `note`, `healthKitCorrelationUUID?` | Carbs are also written to Apple Health as a food correlation. |
| `MealItem` | `name`, `carbsGrams`, `servings` | v1 adds a food-database reference. |
| `MealResponse` | `meal`, `baselineMgdL`, `peakMgdL`, `delta`, `minutesToPeak`, `hadWalkAfter`, `confidence` | Computed and cached after the 2–3-hour window closes. `confidence` is low with fingersticks. |
| `DailySummary` | `date`, `mean`, `inRangeFraction`, `lows`, `highs`, `readingCount`, `cgmCoverage`, `steps`, `activeMinutes`, `sleepHours` | Cached per day so 30-day charts stay instant; rebuilt when its inputs change. |
| `Reminder` | `id`, `kind` (glucoseCheck/medication/activity/hydration/postMealWalk), `title`, `hour`, `minute`, `weekdays`, `minutesAfterMeal`, `isEnabled` | Stored as JSON in the App Group defaults. Medication reminders hold a free-text label only. There is no dose field, by design. |
| `UserProfile` | `unit`, `targets: TargetRange`, `stepGoal`, `activeMinutesGoal`, `usesCGM`, care contact, `acceptedDisclaimerVersion`, `acceptedDisclaimerAt` | Stored as JSON in the App Group defaults so widgets and the Watch can read it. |

### What lives where in Apple Health

| Data | Read | Write | HealthKit type |
|---|---|---|---|
| Blood glucose | ✓ | ✓ manual entries | `bloodGlucose` |
| Carbs | ✓ | ✓ meal logs | `dietaryCarbohydrates`, in a `food` correlation |
| Water | ✓ | ✓ | `dietaryWater` |
| Steps, active minutes | ✓ | — | `stepCount`, `appleExerciseTime` |
| Workouts | ✓ | — | `HKWorkoutType` |
| Heart rate | ✓ | — | `heartRate` (v1, for workout context) |
| Sleep | ✓ | — | `sleepAnalysis` (v1) |

**Two details that matter:**
- **Reading context needs the app's own field.** HealthKit's meal-time metadata
  (`HKMetadataKeyBloodGlucoseMealTime`) only has *before meal* and *after meal*.
  The app writes those when they apply and keeps the full context (fasting,
  bedtime) in its own metadata key and in SwiftData.
- **Edits must not create duplicates.** Each manual entry gets a stable
  `HKMetadataKeySyncIdentifier` plus a version number, so editing an entry
  replaces the sample in Apple Health instead of adding a second one.

## 6. Key flows

**Glucose import**
1. On launch, and when a background observer fires, the app runs an anchored
   query that returns new and deleted samples since its last saved anchor.
2. It upserts them into SwiftData by `healthKitUUID`.
3. It recomputes the `DailySummary` rows for the affected days.
4. It writes a fresh App Group snapshot and reloads the widget timelines.

**Manual entry**
1. The app validates the value (rejects anything outside 20–600 mg/dL as a likely
   typo, and confirms values under 54 or over 300).
2. It saves to Apple Health, mirrors the sample, then checks the safety rules.
3. If the reading is urgent, the urgent guidance screen appears *before*
   returning to the dashboard.

**Meal response**
1. When a meal is logged, the app records the baseline: the last reading in the
   30 minutes before the meal.
2. With CGM, the app finds the peak within 3 hours of the meal.
3. With fingersticks, it schedules a "check 2 hours after your meal" reminder.
4. It stores a `MealResponse` and compares the same meal with and without a walk
   afterwards over time. The app phrases this as "after this meal your glucose
   rose about 60 mg/dL", never as cause and effect.

**Watch**
- The Watch reads its own copy of Apple Health, which iOS syncs to it over time.
- WatchConnectivity carries settings (units, targets) and quick logs when the
  phone is reachable.
- Quick logs from the wrist are written straight to the Watch's Apple Health,
  which syncs them back to the phone, so nothing is lost when the phone is away.

## 7. Safety design

- **First-launch disclaimer.** A clear, plain-language disclaimer the user must
  accept, versioned so material changes re-prompt. It is also always reachable
  from Settings and shown in the PDF report.
- **No dosing anywhere.** No insulin or medication calculators, and no field that
  stores a dose. The tests include a check on the copy strings for dosing language.
- **Urgent screen.** A reading below `urgentLow` or above `urgentHigh` opens a
  full-screen urgent guidance screen:
  - "Follow your care plan for low/high blood sugar."
  - "If you feel unwell, confused or faint, call emergency services."
  - A one-tap call to the user's saved care contact and to the local emergency
    number.

  The exact wording, and whether to include the "15-15 rule" for lows, is for
  the clinical reviewer to sign off (see open questions).
- **Stale data is labeled.** Every displayed reading shows its age. Readings older
  than 20 minutes (CGM) are greyed out with "Last reading 2 h ago", and
  complications show the reading time rather than a bare number.
- **Suggestions are general and cautious.** Diet and exercise content is general
  education reviewed by a clinician, includes "check with your doctor before
  starting new exercise", and never adapts to a reading in a way that would
  amount to treatment advice (no "your glucose is 250, go for a run").

## 8. Privacy

- **HealthKit permissions on first need, with a primer.** Each request comes when
  the user first needs it, after a screen explaining why. The app keeps working
  with partial permissions; for example, without sleep access it hides the sleep
  correlation.
- **Purpose strings are specific.** `NSHealthShareUsageDescription` and
  `NSHealthUpdateUsageDescription` say exactly what is read and written and why.
- **Privacy declarations are minimal.** `PrivacyInfo.xcprivacy` lists only the
  required-reason APIs actually used. The App Store privacy label is
  "Data Not Collected".
- **Protected storage.** The SwiftData store and meal photos use iOS's default
  data protection (encrypted until the phone is first unlocked after a restart).
  Full `NSFileProtectionComplete` would stop background Apple Health updates
  from saving while the phone is locked.
- **Optional app lock.** A Face ID lock is optional, off by default.
- **No data leaves the device.** No analytics, crash reporting with health
  payloads, or advertising SDKs. The PDF report is only shared when the user taps
  the share sheet.

## 9. Testing

- **Unit tests (GlucoseKit, no simulator):** unit conversion round-trips, range
  classification at boundaries, time in range and GMI against published worked
  examples, estimated-A1C guards for too few readings, trend arrow from synthetic
  CGM traces, meal-response windowing, stale-data thresholds.
- **View model tests:** run against `MockHealthService` with fixture data covering
  weeks of CGM, sparse fingersticks, empty data and denied permissions.
- **UI tests:** onboarding, manual entry → urgent screen, PDF export.
- **CI:** GitHub Actions on a macOS runner runs `xcodegen`, then `xcodebuild test`
  for the package and the iOS scheme.
